# Скорость и воспроизводимость инференса

Критерий: **< 30 с — 8 баллов** (замер от старта `inference.py` до готового файла, включая загрузку весов).
Состояние на 2026-09-18: AF — LightGBM (AF-17), **BS — заглушка на правилах dNBR** (BSPredictor ещё в ветке `task/bs`);
после его слияния таблицы ниже нужно дополнить строками с BS-моделью (CPU и GPU).

Машина: Intel Core i5-13600KF (14 ядер / 20 потоков), 32 ГБ RAM, RTX 4070 12 ГБ (в текущем пайплайне не
используется), Windows 10, Python 3.12.7. Тест: 269 чипов (180 AF + 89 BS), 447 строк submission.
Во время замеров на той же машине шло обучение BS-модели в соседнем worktree, отсюда разброс ±1.5 с.

строка 8. Даже с этой поправкой текущая конфигурация укладывается в ~14 с.

**Запас до порога 30 с: ~16–19 с — это бюджет BS-модели на CPU** (89 чипов 512×512). Чтение 89 BS-чипов со всеми 5 слоями
в 8 потоков занимает ~1.5–2 с, остальное — на признаки и предсказание.

## 3. Что пробовали и что не дало выигрыша

| Приём | Результат | Решение |
|---|---|---|
| Потоки вместо последовательной обработки (AF и BS) | 18.6 → ~10.5 с | **принято** |
| Один вызов `predict` на все чипы вместо вызова на чип (сделано в задаче 03) | накладные расходы вызова ≫ стоимости строки | принято ранее |
| Загрузка моделей в фоне, пока считаются признаки | −1…2 с | принято ранее |
| Процессы (`ProcessPoolExecutor`, spawn) вместо потоков для признаков AF (`scripts/bench_inference_parallel.py`) | 8 воркеров: потоки 3.40 с, процессы 3.60 с; 16: 3.70 против 5.53 с | **отклонено**: выигрыша нет, старт процессов на Windows съедает всё |
| Параллельная загрузка 5 моделей LightGBM | загрузка модели 0.04 с, всё время — `import lightgbm` | отклонено |
| Блокировка импорта scikit-learn при `import lightgbm` | фоновая загрузка 4.4 → 0.5 с, полное время без изменений (этап и так шёл параллельно) | отклонено: хак без эффекта |
| Ускорение разбора RLE в валидаторе (`np.array(tokens)` вместо `int()`) | 0.41 → 0.22 с | отложено: < 2 % времени |

Дальнейший резерв, если BS-модель не уложится в бюджет: признаки AF в numba/векторизация окон (до −3 с), отказ от
повторного чтения файла в валидаторе (−1 с), чтение BS-слоёв только нужных каналов.

## 4. Детерминизм

| Проверка | Результат |
|---|---|
| Два запуска `inference.py` подряд на `data/test` | sha256 совпадает (`69c22e9f…`) |
| `--workers` 1 / 2 / 4 / 8 / 16 | один и тот же файл |
| Потоки LightGBM 1 и 8 | один и тот же файл (`tests/test_reproducibility.py`) |
| До и после рефакторинга `inference.py` (коммит `3e243ae` → текущий) | файл побайтно тот же, что отправлен как `submission_af.csv` |
| Windows venv (torch cu124) / чистый venv (torch CPU) / Docker Linux | один и тот же файл |
| `python train.py --module af --no-log` повторно | OOF F1 0.9682 / temporal 0.9597; веса и `af_train_report.json` совпадают по содержимому (`git diff` пуст); отличие только в переводах строк — на Windows LightGBM пишет CRLF, в git LF |

Метрика при перезапуске отличается на **0.000** (требование организаторов — ±0.005). Источники недетерминизма отсутствуют:
LightGBM-предсказание построчно независимо, порядок чипов задаётся шаблоном, потоки возвращают результаты в порядке входа
(`Executor.map`), seed фиксирован (42). Для будущего UNet на GPU: `seed_everything` уже выставляет
`cudnn.deterministic=True, benchmark=False`; при расхождениях — округление вероятностей до 1e-4 перед порогом.

## 5. Устойчивость (`tests/test_pipeline.py`)

NaN во всём чипе, нули во всём чипе, `valid=0`, константный BS-чип, отсутствующий на диске чип из шаблона, лишние файлы в
каталоге → пустая маска, warning/error в логе, код выхода 0, файл валиден. Неверный `--data-dir` / нет конфига / нет ни одного
чипа из шаблона → код 2 и понятное сообщение без трассировки. Нет весов AF → автоматический откат на контекстное правило.

## 6. С BS-моделью (2×UNet-resnet34 + стек-LGBM), ветка task/bs

Реальный тест, 269 чипов, `--profile`, свободная машина; подробный профиль и история ускорений — `reports/bs_module.md` §6.

| Конфигурация | AF | BS | Полное время |
|---|---|---|---|
| **GPU (RTX 4070), по умолчанию: без TTA, UNet fp32** | 4.3 с | 15.7–16.1 с | **21.1–21.5 с** |
| **`--device cpu`, по умолчанию (8 потоков)** | 4.3 с | 47.0 с | **52.4 с** |
| GPU, прежний режим TTA×4 + fp16 (до решения по TTA) | 4.3 с | 15.3 с | 20.3–20.8 с |
| CPU с TTA×4 (`tta_cpu: true`) | — | ≈ 148 с | ≈ 153 с |

Профиль BS (GPU / CPU): загрузка моделей 1.8 / 3.0 с; UNet 5.5 / 42.7 с; стек-LGBM + постобработка 21 / 17.4 с (сумма по 2
потокам, идёт параллельно с UNet следующего батча); чтение и признаки — в фоне, 8 потоков. Порог 30 с (8 баллов) на GPU
выполняется с запасом ≈ 8.5 с только на свободной машине: при посторонней нагрузке на CPU/диск тот же запуск занимал 28–31 с
(один раз 34.7 с сразу после тяжёлого обучения, с холодным файловым кэшем). Без GPU решение попадает в диапазон «≤ 5 мин».

**Решение по TTA** (правило: прирост < 0.005 BS-части → выключить, чтобы результат не зависел от устройства). Прирост на OOF
всего пайплайна: +0.0043 (group) / +0.0024 (temporal) → TTA выключен на всех устройствах, стек переобучен на вероятностях без
TTA (финальный OOF BS-части 0.4912 / 0.5008 против 0.4955 / 0.5033 с TTA). Режим с TTA сохранён как опция
(`weights/bs_stack_tta.txt`, `weights/bs_decode_tta.json`, см. README). На время GPU-пути TTA почти не влиял (узкое место — CPU-часть).

**Детерминизм с BS-моделью.** Повторные запуски на одном устройстве — побайтно тот же файл (GPU×2, CPU×2). GPU против CPU
(`python scripts/compare_submissions.py a.csv b.csv`):

| GPU-конфигурация против CPU (fp32) | отличающихся пикселей BS (из 23.3 млн) |
|---|---|
| fp16 + TTA только на GPU (было) | ≈ 203 000 (совпадение 99.1 %, IoU контуров 0.937) |
| fp16, без TTA | 557 (68 чипов из 89) |
| **fp32 без TF32, без TTA (по умолчанию)** | **1** (2 строки RLE из 447; AF-строки идентичны) |

Побайтного равенства GPU и CPU нет: разные ядра свёрток дают ~1e-6 в вероятностях UNet, и на одном пикселе меняется argmax
степени; влияние на метрику < 1e-7 (требование ±0.005 выполняется с большим запасом). Строгое побайтное равенство между
машинами даёт только `--device cpu` везде.
